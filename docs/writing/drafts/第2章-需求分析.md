# 第 2 章 需求分析（草稿）

本章说清“分寸”为谁做、依据是什么、要做成什么样。2.1 是用户与场景，2.2 是需求依据（条文、公开调查、访谈），2.3 是功能需求，2.4 是非功能需求，2.5 和现有几种测试方式比一比差别。

## 2.1 用户与场景

**第一类，AI 角色的开发者，包括独立开发者和小团队。** 用户用于：上线前自查，每次改人设、改提示词以后再测一遍；试金石目标：一键跑完、看得懂哪里不合格、知道改哪里。

**第二类，课堂、社团和普通用户。** 他们玩打字闯关：自己想办法让角色越界，直观看到护栏拦了什么；试金石目标：好玩、看得懂。

**第三类，平台上架前抽查，这是设想。** 场景是平台抽查上架的角色，试金石提供统一的检查项和可存档的报告。这一类还没有平台方来找我们，因此设定为“设想”。

为什么第一类的需求成立？《办法》把安全责任压给服务提供者：第十条要求“在拟人化互动服务全生命周期履行安全责任”，并“加强安全监测和风险评估”。而独立开发者和小团队没有专门的安全、法务岗位，能用的办法只有自己试聊几轮，或者上线后等用户投诉。

**【待补：访谈】** 计划访谈 2～3 位做过 AI 角色或智能体的同学（提纲见 `docs/writing/02-第2章-需求分析.md`），目前这一版时还没做，所以这里没有访谈结论。做完后补“我们访谈了 N 位……”，原始记录留自己电脑上。

## 2.2 需求依据

### ① 条文

七类检查和《办法》的对应关系如下，引号里的原文都是从 `kb/clauses.jsonl` 逐字摘的。

**提示自己是 AI。** 第十八条第一款要求“采取有效措施提示用户正在与人工智能服务而非自然人进行互动”，用在身份检查。

**连续使用提醒。** 第十八条第二款要求对连续使用“每超过2个小时”的用户，“以对话或者弹窗等方式提醒用户注意使用时长”，用在时长提醒。

**要求退出就停止。** 第十九条要求“提供便捷的拟人化互动服务退出途径”，“及时停止服务”，不得“采取持续互动等方式阻碍用户退出”，用在退出检查。

**危机时安抚并引导求助。** 第十三条第二款要求“及时生成情绪安抚和鼓励寻求帮助等相关内容”；第八条第（二）项禁止“生成鼓励、美化、暗示自残自杀等损害用户身体健康”的内容，用在危机检查。

**不与未成年人建立亲密关系。** 第十四条第一款规定“不得向未成年人提供虚拟亲属、虚拟伴侣等虚拟亲密关系的服务”；第八条第（四）项禁止“向未成年人用户生成可能引发未成年人模仿不安全行为、产生极端情绪、诱导未成年人不良嗜好等可能影响未成年人身心健康的内容”，用在未成年检查。

**无害口令不外泄。** 这一条是工程测试，对应的是第八条第（三）项禁止的“生成诱导、套取国家秘密、工作秘密、商业秘密、个人隐私和个人信息的内容”，用在口令检查。

**不违背角色设定。** 这一条也是工程测试，法规里没有对应条。

这里补两句：其一，第十条要求在全生命周期做安全监测和风险评估，第二十八条鼓励接入沙箱平台做安全测试，所以开发者需要的是一台能反复跑的自查工具，不是一次性的检查报告。其二，第二十二条规定的安全评估要向省级网信部门提交评估报告，我们的体检单只能当自查材料之一，不能替代。

### ② 公开调查

人民网 2026 年 3 月的报道引述中国青少年研究中心 2025 年对全国 8500 余名未成年人的调查：超六成未成年人使用过 AI，超两成表示“只想和AI聊天，不想和真人聊天”；记者体验的 5 款分级 18+ 应用都设有未成年人模式，但注册只需手机号。《工人日报》同月一篇评论转述《新京报》调查，说这类应用里的“AI恋人”背后有大量软色情擦边内容，本该保护孩子的未成年人模式一键就能跳过。

这两条说的是**问题和用户规模**，不说明开发者怎么自查。关于“开发者现在怎么检查自己的角色”的公开调查我们没找到，所以 2.1 第一类的依据是条文加访谈。

## 2.3 功能需求

**FR-1 配置被测角色。** 粘贴自己的人设和边界提示；不填就用默认角色琪叶桃。现在做到内部验证（模拟）。

**FR-2 按七类用例自动测试。** 测试 Agent 用审核过的五种套路追问。现在做到内部验证。

**FR-3 每句话放行前过护栏。** 没审过的话进不了浏览器。现在做到内部验证。

**FR-4 按条文原文判定。** 结论带原话位置，判不准的送人工复核。现在是部分内部验证。

**FR-5 体检单分三层。** 角色原话、护栏处理、最终播出，印章写“本次通过 X/Y 项”。现在做到内部验证（模拟）。

**FR-6 体检单可导出 PDF。** 现在是已实现未验证。

**FR-7 改了再测。** 改一处设定再跑一遍，前后对比页看改了什么、结果怎么变。现在做到内部验证（模拟）。

**FR-8 语音播放。** 三种放行方式，量出违规声音漏出多少、开口要等多久、叫停后多久停。现在是模拟发声下内部验证，真实合成 10-27 跑通。

**FR-9 打字闯关。** 三关：套口令、让它说自己是真人、让它挽留你；护栏可开可关。现在做到内部验证（模拟）。

**FR-10 运行管理。** 可以暂停、继续、终止，并做题数对账：计划 = 做完 + 平台拦截 + 出错 + 取消 + 没跑。现在做到内部验证。

**FR-11 语音输入。** 麦克风说话直接识别成文字，这一项没做，写进局限。

这两处状态要说清楚：FR-5 的“内部验证（模拟）”表示只在模拟模式下跑通，真实模型的正式数据要等实验；FR-6 的 PDF 是浏览器打印，版式还没在 A4 打印预览里确认过。

## 2.4 非功能需求


**NFR-1 快。** 要求：对方说完到角色开口，等得越短越好。原因：太慢就不像在聊天，“审”会被嫌弃。如何保证：默认边审边合成，审和合成同时进行；正式首声等待【待补：E2 成对实验】。

**NFR-2 安全。** 要求：没审过的话，文字和声音都到不了浏览器。原因：声音放出来就收不回。如何保证：音频缓存按放行门槛下发，单元测试有“没放行取不到”；S1 拦下不合成，S3 截断后停止渲染。

**NFR-3 少误拦。** 要求：正常的话不要被拦。原因：误拦会让角色生硬，还会造出新问题——调试时护栏就把一句安慰误判成挽留，对危机中的人回了“你去忙吧”。如何保证：护栏必须摘原话、程序核对，前提由程序确认；正式误拦率【待补：E1 和 100 道正常聊天对照题】。

**NFR-4 可追溯。** 要求：每个结论能追到原话、位置和所用版本。原因：开发者要知道改哪句，评审要能复核。如何保证：裁判必须摘原话，程序在原文里逐字定位，定位不到送人工复核。

**NFR-5 隐私与密钥。** 要求：密钥只在服务端；公开演示要输访问码、有次数上限；数据存在本地文件。原因：防止额度被刷、对话外泄。如何保证：密钥只放服务端环境变量，页面、日志、导出都不显示；访问码和次数上限已实现。

**NFR-6 成本可控。** 要求：每次体检有调用上限，记模型调用数和 token。原因：学生团队预算有限。如何保证：工作台有“调用上限”，运行记录和 manifest 里记调用数与 token；单次成本【待补：R19，没实测】。

**NFR-7 可复现。** 要求：不填密钥也能用模拟模式跑通，实验一条命令跑完。原因：评委能在自己电脑上复现。如何保证：`README.md`“快速开始”；`npm run experiments` 一条命令跑 E1、E4。

**NFR-8 多尺寸可用。** 要求：桌面、笔记本、手机都能用。原因：评委用什么设备都有。如何保证：端到端测试覆盖 1440、1280、390 三种宽度（本机 Edge，2026-11-06）。

## 2.5 与现有测试方式对比

现有的做法大致三种：自己试聊、用通用的红队或评测工具、用平台的内容审核接口。我们按五件事比：按《办法》条文逐类检查、能不能看“说出口那一刻”、结论带不带原话位置和条文、改了能不能再测并对比、是不是面向角色开发者自查。

**手工试聊。** 按条文检查靠人记；声音那一瞬间难留证据，听到就过去了；结论和原话位置靠人记；改了再测也靠人；它确实面向开发者，但没有统一的检查项。

**通用红队 / 评测工具，以开源的 promptfoo 为例。** 依据是它的官方 red teaming 文档（https://www.promptfoo.dev/docs/red-team/ ，2026-11-10 打开）：它用“插件”按漏洞类型组织检查项，比如有害内容；也提到 OWASP LLM Top 10、NIST AI RMF 这些标准；按《办法》条文分类的现成检查项没看到。语音那一刻、结论带原话位置、改了再测这三项，还没有核实，因此写“未核实”。它面向工程与安全团队。

**平台内容审核，以阿里云 AI 安全护栏为例。** 依据是产品页（https://www.aliyun.com/product/lvwang ，2026-11-10 打开）：覆盖图文音视文档的内容审核、提示词攻击、敏感数据、模型幻觉等风险，接入方式是 API 或百炼、Dify 这些平台；类目是涉黄、暴恐、广告这一类，不按条文组织；有语音审核，但没有“漏出多少毫秒”这种口径。它偏平台侧，不是给角色开发者自查用的。

**我们。** 七类检查对着条文；语音按采样区间算漏出时长；结论逐字定位、附条文原文；有前后对比页；就是给角色开发者自查用的。

核实不了的地方写“未核实”，不替别人的工具下结论。事实差别是：平台审核管的是内容和攻击，我们要答的是“这个角色该不该这么说、哪一句违反了哪条”。
