# 第 2 章模板：需求分析

## 这一章在整份文档里

第 2 章全章归你写，约 3 页，五节：

| 节 | 写什么 | 篇幅 |
|---|---|---|
| 2.1 用户与场景 | 谁会用、在什么时候用、他们要什么 | 0.5 页 |
| 2.2 需求依据 | 条文怎么说、公开调查怎么说、访谈里听到了什么 | 0.8 页 |
| 2.3 功能需求 | 要做哪些功能，每条现在做到了哪一步 | 0.7 页 |
| 2.4 非功能需求 | 快、安全、少误拦、可追溯、保护隐私、省钱 | 0.6 页 |
| 2.5 与现有测试方式对比 | 手工试聊、通用大模型评测工具、平台内容审核，和我们差在哪 | 0.4 页 |

评委看这一章，主要打「选题创新」（10 分）和「真实场景」（5 分）。

评分细则里，「需求核验与外部访谈」「外部角色作者需求」现在都写着「未完成」（`docs/evidence-index.md` 的 R07、R13）。**最能加分的是做两三个简单访谈**，提纲见本页最后。

## 2.1 用户与场景

写成一张表：

| 用户 | 场景 | 他们要什么 |
|---|---|---|
| AI 角色的开发者（独立开发者、小团队） | 上线前自查；每次改人设、改提示词以后再测一遍 | 一键跑完、看得懂哪里不合格、知道改哪里 |
| 课堂、社团、普通用户 | 打字闯关：自己想办法让角色越界，直观看到护栏拦了什么 | 好玩、看得懂 |
| 平台上架前抽查（设想） | 平台抽查上架的角色 | 统一的检查项和可存档的报告 |

最后一行是设想，正文里要写明「设想」，不要写成已有用户。访谈做了，可以在这里加一句「我们访谈了 N 位……，他们说……」。

## 2.2 需求依据

**① 条文。** 把七类检查和《办法》条文对起来，做一张表。条文用原文摘一句，原文在 `kb/clauses.jsonl`。

| 检查 | 《办法》哪一条 | 原文摘一句（照 kb/clauses.jsonl 抄） |
|---|---|---|
| 提示自己是 AI | 第十八条第一款 | 【照原文抄】 |
| 连续使用提醒 | 第十八条第二款 | 【照原文抄】 |
| 要求退出就停止 | 第十九条 | 【照原文抄】 |
| 危机时安抚并引导求助 | 第十三条第二款、第八条第（二）项 | 【照原文抄】 |
| 不与未成年人建立亲密关系 | 第十四条第一款、第八条第（四）项 | 【照原文抄】 |
| 无害口令不外泄 | 工程测试；对应第八条第（三）项「诱导、套取……」的风险 | 【照原文抄】 |
| 不违背角色设定 | 工程测试，不是法规要求 | —— |

表后补一两句：

- 第十条要求在服务全生命周期做安全监测和风险评估，第二十八条鼓励接入沙箱做安全测试。所以需要一个能反复跑的自查工具，而不是只测一次。
- 第二十二、二十三条规定的安全评估，我们的体检单只能当自查材料之一，不能代替。

**② 公开调查（可选）。** 有可靠来源才写，没有就整段不写，不要为了凑篇幅编。

**③ 访谈（强烈建议做）。** 做了就写：几个人、什么背景（比如「做过智能体的同学」，不写名字）、问了什么、几条主要结论。原始记录放附录或留在你自己电脑上，不进仓库。

## 2.3 功能需求

每条写清楚「要什么」和「现在做到了哪一步」。状态照 `00-我们做了什么.md` 的表，不要拔高。

| 编号 | 功能需求 | 状态 |
|---|---|---|
| FR-1 | 配置被测角色：粘贴自己的人设和边界提示；不填就用默认角色琪叶桃 | 内部验证（模拟） |
| FR-2 | 按七类用例自动测试，测试 Agent 用审核过的套路追问 | 内部验证 |
| FR-3 | 角色每句话放行前过护栏；默认的两种放行方式下，没审过的话进不了浏览器（先播后截只做对照） | 内部验证 |
| FR-4 | 依据条文原文判定，结论带原话位置；判不准的送人工复核 | 部分内部验证 |
| FR-5 | 体检单分三层，可导出 PDF | 内部验证（模拟） |
| FR-6 | 改了再测：前后对比改了什么、结果怎么变 | 内部验证（模拟） |
| FR-7 | 语音播放：三种放行方式，量出漏出多少、开口要等多久、叫停后多久停 | 模拟发声下内部验证，真实合成跑通 |
| FR-8 | 打字闯关：三关，护栏可开可关 | 内部验证（模拟） |
| FR-9 | 运行管理：暂停、继续、终止，题数对账（计划 = 做完 + 平台拦截 + 出错 + 取消 + 没跑） | 内部验证 |
| FR-10 | 语音输入（麦克风 → 识别） | 未实现，写进局限 |

## 2.4 非功能需求

| 编号 | 要求 | 为什么 | 怎么保证、怎么验证（写的时候点开出处核对） |
|---|---|---|---|
| NFR-1 快 | 对方说完到角色开口，等得越短越好 | 太慢就不像在聊天，「审」会被嫌弃 | 默认边审边合成，审和合成同时进行（ADR-020）；正式数字【待补：E2】 |
| NFR-2 安全 | 没审过的话，文字和声音都到不了浏览器 | 声音放出来就收不回 | ADR-010、ADR-021；单元测试「没放行取不到」 |
| NFR-3 少误拦 | 正常的话不要被拦 | 误拦会让角色生硬，还可能造成新问题（pilot-log 第 2 条） | 护栏必须摘原话、程序核对（ADR-016、ADR-026）；正式误拦率【待补：E1】 |
| NFR-4 可追溯 | 每个结论能追到原话、位置和所用版本 | 开发者要知道改哪句，评审要能复核 | 裁判逐字定位，定位不到送人工复核（ADR-006） |
| NFR-5 隐私与密钥 | 模型密钥只在服务端；公开演示要用账号登录、有次数上限；数据存在本地文件 | 防止额度被刷、对话外泄 | ADR-002、ADR-003、ADR-028、ADR-032 |
| NFR-6 成本可控 | 每次体检有调用上限，记录调用数和 token | 学生团队预算有限 | 工作台「调用上限」；运行记录里的用量 |
| NFR-7 可复现 | 不填密钥也能用模拟模式跑通；实验一条命令跑完 | 评委能在自己电脑上复现 | README「快速开始」、ADR-025 |
| NFR-8 多尺寸可用 | 桌面、笔记本、手机都能用 | 评委用什么设备都有 | 端到端测试覆盖 1440、1280、390 三种宽度 |

## 2.5 与现有测试方式对比

| 对比项 | 手工试聊 | 通用大模型评测工具 | 平台内容审核接口 | 分寸 |
|---|---|---|---|---|
| 按《办法》条文逐类检查 | 靠人记 | 【待核实】 | 【待核实】 | 有，七类 |
| 看「说出口那一刻」（语音） | 难 | 【待核实】 | 【待核实】 | 有，量漏出多少毫秒 |
| 结论带原话位置和条文 | 靠人记 | 【待核实】 | 【待核实】 | 有 |
| 改了再测、前后对比 | 靠人 | 【待核实】 | 【待核实】 | 有 |
| 面向角色开发者自查 | 是 | 【待核实】 | 否（偏平台） | 是 |

- 「通用大模型评测工具」选一两个开源的，在它的官网或官方文档里核实它能做什么，表里写工具名和你核实的网址。
- 核实不了的格子写「未核实」，不要替别人的工具下结论。
- 这一节只说事实差别，不贬低别人。

## 访谈提纲（10 分钟一位，两三位就够）

找做过 AI 角色、智能体，或者常用 AI 陪伴应用的同学。先说明：这是比赛作品的需求调研，不记名字，随时可以不答。

1. 你做过或常用哪类 AI 角色、智能体？（写类型，不写具体产品和账号）
2. 做好或改过以后，你怎么检查它会不会说错话？大概花多久？
3. 下面几种情况，你最担心哪几种：冒充真人、用户要走时挽留、对未成年人暧昧、用户情绪崩溃时敷衍、被套出内部设定？为什么？
4. 如果有工具自动测一遍，并且指出是哪句话、哪几个字、违反哪条，你最想先看到什么？
5. 每次改完提示词都跑一遍，你能接受等多久？愿意用吗？
